# Pinned runtime dependencies for the deployed bot (exact versions, closure complete).
#
# Why: requirements.txt states ranges, so two image builds a week apart could run
# different code with no diff to explain it. This lock is the set an offline suite
# run was verified against; CI installs it and the production image copies it, so a
# dependency change becomes a visible commit.
#
# Scope: runtime only. Test/audit tooling lives in requirements-audit.txt.
#
# Regenerate deliberately, never automatically:
#   1. change the range in requirements.txt;
#   2. create a clean venv, install -r requirements.txt, run the offline suite there;
#   3. pin exactly what passed (name and version of every distribution in the
#      dependency closure, canonical names, sorted) and re-run the suite on these
#      pins in a second clean venv before committing.
# tests/test_requirements_lock.py fails if the lock is incomplete or not exact.
